# ⚡ QuizBlitz

Командная мультиплеерная викторина: ведущий создаёт комнату, друзья заходят по шестизначному коду или QR, отвечают на вопросы и видят общий рейтинг. Вопросы может подготовить ИИ; без API-ключа игровой сервер использует резервный банк.

## Текущее состояние

| Возможность | Статус |
| --- | --- |
| Главная, гостевой вход, формы регистрации/логина | Фронтенд готов; по умолчанию локальное демо авторизации |
| Создание комнаты, код/QR, общий список участников, старт ведущим | Работает с реальным Socket.IO-сервером |
| Вопросы, ответы, серверный таймер, очки, рейтинг, подиум | Реализованы; проверяются двумя браузерными клиентами |
| Профиль и история | Интерфейс и REST-адаптер готовы; локальные результаты сохраняются только для демо-игр |
| REST-авторизация, серверный профиль и история | Пока отсутствуют: Python `app/main.py` и `app/api/__init__.py` пустые |
| База данных | Добавлены SQLAlchemy-модели и миграция; игровой сервер пока не сохраняет результаты в БД |
| Генерация ИИ | Есть серверный провайдер; требует отдельного API-ключа. Автотесты используют резервные вопросы |

Демо-авторизация не создаёт настоящие аккаунты и не проверяет пароли. Переключение `VITE_AUTH_MODE=live` само по себе не реализует серверные эндпоинты.

Часть Nonwire находится в `frontend/src/components/portal`. Общие `App`, `useGameEngine` и Socket.IO-адаптер связывают лобби с существующими игровыми экранами. `frontend/src/components/game` и исходники `backend` при этой интеграции не изменяются. Общая типографика и адаптивные стили собраны в `frontend/src/portal.css`.

## Требования

- Node.js **22.12+** (проверено на Node 24) и npm.
- Для браузерных тестов: Google Chrome на macOS; Chromium Playwright на Linux/Windows.
- Для текущего игрового демо PostgreSQL, Python и ключ ИИ **не нужны**.

Установка из корня репозитория:

```sh
npm --prefix backend ci
npm --prefix frontend ci
```

## Запуск фронтенда вместе с игровым сервером

Терминал 1:

```sh
cd backend
npm run dev
```

Сервер: `http://localhost:3001`. Проверка готовности: `http://localhost:3001/health`.

Терминал 2:

```sh
cd frontend
cp .env.example .env.local
```

В `frontend/.env.local`:

```dotenv
VITE_GAME_MODE=live
VITE_AUTH_MODE=demo
VITE_BACKEND_URL=http://localhost:3001
VITE_API_URL=http://localhost:8000
```

```sh
npm run dev -- --host 0.0.0.0
```

Открыть адрес, напечатанный Vite, обычно `http://localhost:5173`.

1. В первой вкладке нажать «Создать игру», указать ник, тему, число вопросов и сложность.
2. Скопировать приглашение из лобби.
3. Открыть его в другом браузере или отдельном приватном окне и войти с другим ником.
4. Убедиться, что оба игрока появились в общем списке. Только ведущему доступна кнопка «Начать игру».
5. Пройти вопросы до подиума. Баллы и переходы live-игры подтверждает сервер.

Для телефонов в одной сети открыть **LAN-адрес компьютера**, а в `VITE_BACKEND_URL` указать тот же IP с портом `3001`. `localhost` на телефоне указывает на сам телефон. После изменения `.env.local` перезапустить Vite. QR использует адрес страницы, открытой у ведущего.

## Локальное демо без бэкенда

Оставить значения из `frontend/.env.example`: `VITE_GAME_MODE=mock` и `VITE_AUTH_MODE=demo`. Затем запустить `npm run dev` из `frontend`.

В демо можно создать комнату, добавить демо-игроков, пройти викторину и увидеть локальную историю. Для входа игроком есть код **849215**. Демо-комнаты изолированы во вкладках: отправка QR другому устройству не создаёт общую сетевую игру. Готовый банк вопросов не зависит от выбранной темы/сложности; при 10 вопросах возможны повторы.

## Настройки

| Переменная | Где | Назначение |
| --- | --- | --- |
| `VITE_GAME_MODE` | frontend | `mock` — локальная игра; `live` — Socket.IO |
| `VITE_AUTH_MODE` | frontend | `demo` — локальный профиль; `live` — REST |
| `VITE_BACKEND_URL` | frontend | URL игрового сервера, обычно `http://localhost:3001` |
| `VITE_API_URL` | frontend | Базовый URL будущего REST API без `/api` |
| `PORT` | backend | Порт игрового сервера, по умолчанию `3001` |
| `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL` | backend | Параметры LLM-провайдера |

`VITE_*` попадают в браузерный код: серверные API-ключи в них не размещать. Для ИИ скопировать `backend/.env.example` в `backend/.env` и задать параметры своего провайдера. Без ключа используется резервный банк. Наличие провайдера не означает, что внешний ИИ проверен: в текущих тестах внешние LLM-запросы отключены.

## Проверки

Из корня репозитория:

```sh
npm --prefix backend test
(cd backend && npx tsc --noEmit)
npm --prefix frontend run lint
npm --prefix frontend run build
npm --prefix frontend run test:e2e
```

Для проверки TypeScript бэкенда также можно выполнить `npx tsc --noEmit` непосредственно из `backend`. В существующем `backend/package.json` команда `build` заканчивается на `|| true`, поэтому её код возврата не подходит как единственная проверка компиляции.

На Linux/Windows перед E2E установить браузер из `frontend`:

```sh
npx playwright install chromium
```

Playwright автоматически запускает и останавливает серверы на изолированных портах **3101, 5180, 5181, 5182**; оставьте их свободными. Запущенное вручную демо на 5173 не используется. Ключ ИИ в тестовом сервере отключён; база и внешний REST-сервис не требуются.

Набор проверок:

- сервер: подсчёт очков, комнаты, жизненный цикл, полный раунд через Socket.IO;
- фронтенд: вход/валидация, создание/присоединение, QR и буфер обмена, права ведущего, демо-игра и история;
- совместно: два независимых клиента, восстановление ведущего после reload/обрыва связи, три настоящих серверных раунда и одинаковые финальные результаты;
- адаптив: 320, 390, 768, 1024, 1440, 1920 px;
- REST-адаптер: тела запросов, Bearer-токен, профиль/история, выход, 401 и неполный ответ **на тестовых заглушках**;
- текущий сервер: отсутствие `/api/auth/guest` даёт HTTP 404 и понятную ошибку, а не фиктивный успешный вход.

Проверка 11 ноября 2026: **15/15 серверных и 17/17 браузерных тестов прошли**. TypeScript бэкенда и production-сборка фронтенда проходят. Линтер фронтенда завершился без ошибок, с тремя предупреждениями React в `App`, `Account` и `RoomLobby`. Это результат перечисленных сценариев, не подтверждение готовности отсутствующего REST-сервиса или внешнего ИИ.

## Известные ограничения интеграции

- Ведущий на сервере называется «Хост»: текущий `room:create` не передаёт его ник. Для изменения нужен согласованный серверный контракт.
- `room:updated` содержит игроков, но не полные настройки комнаты; вошедшему игроку показывается нейтральная тема без выдуманных параметров.
- Reload в лобби сохраняет комнату и роль. Для полного восстановления игровых фаз reveal/leaderboard/finished серверу нужен snapshot. Не считать восстановление всех фаз реализованным.
- При обрыве связи live-режим не переключается на моки; действия блокируются до подключения.
- JWT передаётся клиентом, но текущий Socket.IO-сервер ещё не проверяет его. До реализации серверной авторизации это учебное демо, а не готовая система аккаунтов.
- В существующем финальном экране «Точность» использует число верных ответов всей комнаты, делённое на количество вопросов; при нескольких игроках возможно значение выше 100%. Персональную статистику нужно согласовать между частью 2 фронтенда и бэкендом. Эта интеграция части 1 не меняет чужой экран подиума.
- История реальных игр не записывается как локальная демо-история. Для неё требуется серверное сохранение и REST API.

## Структура и контракт

```text
frontend/src/components/portal/  # часть Nonwire
frontend/src/components/game/    # игровые экраны karapuz1226
frontend/src/hooks/              # общее состояние лобби и игры
frontend/src/services/           # REST, Socket.IO и явные демо-адаптеры
frontend/tests/                  # браузерные и интеграционные проверки
backend/src/                    # Node.js / Express / Socket.IO
backend/tests/                  # Vitest и Socket.IO-тесты
backend/app/                    # Python: модели и заготовка REST
backend/migrations/             # Alembic
```

Полные ожидаемые REST-ответы, события и правила восстановления описаны в [frontend/INTEGRATION.md](frontend/INTEGRATION.md). Документация игрового сервера: [backend/README.md](backend/README.md).

Работа ведётся в `feature/<ник>-<задача>`. Изменения в командную `main` проходят через Pull Request; по ТЗ перед слиянием требуется ревью другого участника.
